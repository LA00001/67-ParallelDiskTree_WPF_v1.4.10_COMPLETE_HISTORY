# Parallel Disk Tree — v1.4.10 🔥

**Графический сканер файлов и папок Windows** на **C# / WPF / .NET 8** с деревом каталогов, подсчётом байтов, последовательным и параллельным обходом, двумя адаптивными режимами и статистикой производительности.

> В архиве — исходный проект Visual Studio (`ParallelDiskTree.sln`), а не проверенный установочный EXE. Программа читает метаданные: **не удаляет, не переносит и не изменяет** файлы.

## История проекта — с самого первого билда

Началось всё с запроса на **быстрый графический сканер Windows вместо CMD**: разбивать каталог на части, обрабатывать подпапки четырьмя параллельными исполнителями и строить точное дерево размеров файлов. ## Что умеет текущий сканер

- **Графический WPF UI:** дерево папок слева, таблица файлов справа, байты/KiB/MiB/GiB, сортировка, открытие в Проводнике и экспорт дерева CSV.
- **Последовательный режим:** отдельный обход со стеком, один исполнитель.
- **Параллельный режим:** общая очередь каталогов, регулируемые **1–64 исполнителя**, по умолчанию 4.
- **🔥 Адаптивный:** изменение параллельности в одном сканировании, целевая верхняя граница 32.
- **🔥🔥64 Адаптивный:** самостоятельный экспериментальный режим с верхней границей 64; прежний режим до 32 не заменяет.
- **A/B:** последовательный обход против параллельного с выбором порядка запуска.
- **Автобенчмарк:** по умолчанию 1/2/4/8/16/32 × 3 полных повтора с чередованием порядка; медианы и диагностика.
- **⚡ Статистика 3099:** окно рекордов с неоновой диаграммой, общей базой сравнения и таблицей подробных метрик.
- **Семь сворачиваемых панелей**, история открытых папок, отдельно перелистываемая таблица, отзывчивый интерфейс и остановка.

## Установка и запуск

1. Установи **Visual Studio 2022**, компонент **.NET desktop development** и .NET 8 SDK.
2. Распакуй весь ZIP в новую папку, открой **`ParallelDiskTree.sln`**.
3. Выбери `Release | Any CPU` → **Сборка → Пересобрать решение**.
4. Запусти через `Ctrl+F5` (или `F5`), выбери корень и нужный режим сканирования.

Пакет содержит `.sln`, `.csproj`, исходники C#, XAML, GitHub Actions, README и LICENSE (шаблон). Для проверки можно использовать `.github/workflows/windows-build.yml` на `windows-latest`.

## Как устроено сканирование

Приложение перечисляет содержимое через `System.IO.Enumeration.FileSystemEnumerable<T>` и извлекает метаданные из `FileSystemEntry`, **не читая содержимое файлов**. Параллельный движок передаёт обнаруженные подпапки в общую очередь `System.Threading.Channels`; освободившиеся исполнители берут новые задачи. В адаптивных режимах число одновременно работающих исполнителей регулируется во время одного обхода без повторного прохода корня.

Точный размер обычного каталога не известен Windows заранее — он получается суммированием обработанных файлов. Отображаемое значение — **логическая длина** файлов, а не обязательно реально выделенные блоки накопителя.

## Производительность и базовый эталон

В поставляемых исторических измерениях эталоном выбран **первый последовательный проход: 320 990,849 мс (320,990849 с)**. Ускорение каждого режима = `320,990849 / время_режима_в_секундах`.

| Зафиксированный проход | Время | Относительно эталона |
|---|---:|---:|
| Последовательный, исходный эталон | 320,990849 с | 1,00× |
| Параллельный, 16 исполнителей | 61,067 с | ≈5,26× |
| Параллельный, 64 исполнителя | 46,563 с | ≈6,89× |
| 🔥 Адаптивный (до 32) | 34,210 с | ≈9,38× |

**Важно:** это отдельные реальные проходы, а не результаты контролируемого сравнения одной неизменной файловой системы и не медианы. Влияют кэш, фоновые операции и изменения файлов. `🔥🔥64` остаётся в сканере, но ранее исключённый из диаграммы результат не восстанавливается этой версией.

## Портативные журналы и встроенная история

- Исходные исторические данные: `data/historical_runs_v1_4_9.csv` и `data/historical_best_observed.csv` в архиве (первый также встроен в сборку как ресурс).
- При будущих проходах: `logs/` **рядом с работающим EXE**, а не в `%LOCALAPPDATA%`.
- Возможные файлы: `events.log`, `benchmarks_v1_2.csv`, `median_summary_v1_2.csv`, `adaptive_samples_v1_4.csv`.
- Обновление диаграммы дополняет встроенную историю успешными проходами из локальной папки `logs/`; повторные записи не должны увеличивать число прогонов дважды.
- Во время перечисления **нет записи лога на каждый файл**: сохраняются компактные итоги, чтобы не тормозить сканирование.

Для Visual Studio путь логов обычно `bin/Debug/net8.0-windows/logs/` или `bin/Release/net8.0-windows/logs/`.

## Ограничения и корректность

- Сканер не создаёт атомарный снимок Windows: файлы и папки могут измениться между чтениями.
- `IgnoreInaccessible=true` допускает пропуски защищённых объектов без увеличения счётчика ошибок; `0 ошибок` не доказывает абсолютной полноты.
- Жёсткие ссылки могут учитываться повторно. Каталоги, являющиеся точками повторного анализа (junction/symlink), не обходятся для предотвращения циклов.
- Дерево результатов хранится в RAM: большие диски могут потребовать много памяти.
- Много исполнителей не обязательно означает более быстрый проход; данные PDH отражают том в целом, а не только программу, и могут быть недоступны.
- Сканирование файлового содержимого, удаление и перенос **не реализованы**.

## Навигация

Кнопки **«Назад / Далее»** относятся к истории выбранных папок, а отдельные **«Страница / Страница»** — к списку текущей папки (по 500 элементов). Если элементов менее 501, перелистывание страниц недоступно — это нормально.
