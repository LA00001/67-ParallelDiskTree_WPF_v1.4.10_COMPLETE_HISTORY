# История Parallel Disk Tree: от идеи до v1.4.10

## Отправная точка (2026-10-09)

Первоначальная цель — Windows-сканер **с WPF-интерфейсом, а не CMD**, который быстро получает дерево папок и суммы байтов для дальнейшей ручной чистки или переноса данных. Идея пользователя: не ждать последовательного обхода всего корня, а распределять найденные подпапки между исполнителями и повторять разбиение на следующей глубине.

В первой реализации это реализовано не жёстким делением корня на четыре равных участка, а **общей динамической очередью задач**: четыре исполнителя выбирают новые подпапки по мере освобождения. На одной глубине может быть как меньше, так и больше четырёх подпапок; движок остаётся загруженным, насколько позволяет структура дерева и файловая система.

### Возможности самого первого ZIP

- `ParallelDiskTree.sln` и `.csproj` для Visual Studio, C# / WPF / .NET 8.
- Окно с полем корня, кнопками выбора, сканирования, остановки и экспорта CSV.
- Дерево папок, список файлов/папок, реальные логические байты и представление в IEC единицах, счётчики общего числа файлов и папок.
- Четыре исполнителя и распределяемая по глубине очередь каталогов, оперативная индикация статистики.
- Переход к папке через Проводник; программа не изменяет файлы.

### Первый рабочий запуск

Пользователь показал, что ранняя версия обработала примерно **442,59 GiB**, **1 606 699 файлов**, **316 527 папок** примерно за три минуты. Это наблюдение из скриншота, а не точный стандартизированный бенчмарк: длительность была сообщена приблизительно.

## Как развивался проект

1. **Стабильная Windows-сборка (v1.0.1–v1.0.2).** Устранение коллизии WinForms/WPF `Application`, затем отсутствие `System.IO` в движке.
2. **Честное сравнение (v1.1.0).** Отдельный последовательный алгоритм, N=1..64, A/B с сохранением результатов и сменой порядка проходов.
3. **Статистическая серия (v1.2.0).** Автобенчмарк на 18 полных проходов, медианы, очередь, CPU, длительность обработки и простоя по исполнителям.
4. **Удобство просмотра (v1.3.0).** Семь складных секций, освобождение места под содержимое.
5. **Первый адаптивный проход (v1.4.0).** Изменение N во время одной сессии; PDH-метрики, история управляющих решений.
6. **Доработка UI и публикации (v1.4.1–v1.4.3).** Прокрутка, компоновка, позиция окна, исправление `System.IO`, GitHub workflow.
7. **Графическая статистика (v1.4.4).** Самостоятельное неоновое окно с реальными результатами, а не синтетическими числами.
8. **Навигация по папкам (v1.4.5).** История назад/вперёд независимо от пагинации.
9. **Два адаптивных алгоритма (v1.4.6–v1.4.7).** Разные лимиты N=32/64 и исправление ошибки сборки `CS0136`.
10. **Единый эталон (v1.4.8).** Единая база 320 990,849 мс; дополнительные показатели того же прохода; дедупликация истории.
11. **Переносимое хранение (v1.4.9).** Встроенная история и локальные логи рядом с EXE вместо пользовательского AppData, корректировки отображения отдельных исторических замеров.
12. **Полная документация (v1.4.10).** Систематизация истории каждого билда, начиная с ненумерованного первого ZIP.

Продолжительность в таблице иногда округлена до миллисекунд; исходная эталонная длительность сохранена с точностью до тысячных миллисекунды. Поздние результаты **не означают**, что алгоритмы были протестированы на неизменном файловом снимке: часть расхождений объяснима активностью Windows, но нельзя исключить и различий в перечислении данных.

В одном автобенчмарке **18/18 полных проходов завершились с `errors=0`**. Это не означает, что прочитаны все защищённые файлы: `IgnoreInaccessible=true` может молча пропускать каталоги.

### Почему цифры в окне статистики отличаются от старых CSV

- **Диаграмма рекордов** показывает выбранные отдельные проходы, а не медианы всех измерений.
- **Эталон N=1** — первый последовательный замер 320,990849 с, а не последующий лучший проход 141,587 с; последний сохранён в сырой истории, но по требованию не показывается второй точкой.
- Отдельный результат 🔥🔥64 исключён из поставляемых графика и таблицы по пожеланию пользователя. Этот факт не отменяет доступности самого режима до 64 исполнителей.
- Начиная с v1.4.9, журнал обновлений для статистики читается **только из папки приложения**, не из AppData.

## Проверка, безопасность и воспроизводимость

- Все промежуточные версии были исходными архивами; часть ранних билдов впервые компилировалась в Visual Studio на машине пользователя и затем исправлялась по реальным ошибкам компилятора.
- Ни один этап не даёт оснований заявлять подтверждённую Windows-сборку v1.4.10 в этой среде. Для этого есть Visual Studio и GitHub Actions.
- Никакого MFT-режима, SQLite, переноса/удаления файлов либо точного измерения занятого на диске пространства в перечисленных релизах **не появилось** — это были идеи для будущей разработки, не текущие функции.
- Хранение дерева — RAM; исходные логические размеры файлов могут отличаться от физически занятых байтов.
